# Round 3 — Past Experience & Project Grilling
**Interview:** Systems / Low-Level Deep-Dive Company
**Project in focus:** gitlight — a reimplementation of Git's plumbing layer from scratch.

> **Interviewer's mindset:** You built a Git clone. That's either very impressive or very superficial, and I can tell which in 10 minutes. If you understand the internals — content addressing, zlib, DAG traversal, the wire protocol — we'll have a real conversation. If you followed a tutorial and don't know why anything works, this round ends quickly.

## Q1 — The Foundational Question

> "Why rebuild Git's plumbing layer at all? `isomorphic-git` and `libgit2` both exist as production-grade libraries. You could have just used one. What did you actually learn from building gitlight that you couldn't have learned by reading Git's source or documentation?"

*What I want:* A specific answer about what building forced you to understand. Not "I wanted to challenge myself." Examples of strong answers:
- "I didn't understand why objects were content-addressed until I had to implement it — then the deduplication benefit became obvious"
- "I didn't understand zlib's role until I tried to read my own `.git/objects/` directory without decompressing it and got garbage"
- "Building the DAG traversal for `log` made topological sort feel concrete instead of abstract"

---

## Q2 — Byte-Level Walkthrough

> "Walk me through, byte by byte, what happens from `gitlight add file.txt` to an object existing on disk."

*Expected full walk-through — I will stop you if you skip a step:*
1. Read `file.txt` content from disk
2. Construct the object header: `"blob <content-length>\0"` (null byte terminator)
3. Concatenate: `header + content`
4. Compute SHA-1 hash of the full concatenated bytes → 40-char hex string
5. zlib compress the concatenated bytes (DEFLATE)
6. Write compressed bytes to `.git/objects/<first-2-chars>/<remaining-38-chars>`

*If you skip the header format, I'll ask about it.*
*If you say "SHA-1 of just the content," I'll ask why Git includes the header.*

## Q3 — Compatibility Claim

> "You claim gitlight objects are 'fully compatible with real Git.' How did you actually verify that? Did you diff your generated objects against `git cat-file` output on the same content, or is that an untested claim?"

*What I want:* Honest precision. Either:
- "I ran `git cat-file -p <sha>` on objects generated by gitlight and compared them to the same file added with real git — they matched" (strong)
- "I verified the SHA-1 matched for simple cases but didn't do systematic cross-testing" (honest and acceptable)
- "I haven't formally verified it" (honest, but weakens the resume claim)

*If you claim full compatibility without testing methodology, I'll note it.*

## Q4 — LCS Complexity and Git's Heuristics

> "Your diff implementation uses LCS (Longest Common Subsequence), the same approach real Git uses. What's the time and space complexity of your LCS implementation? Does it degrade badly on large files?"

*Expected:*
- Classic LCS: O(m*n) time and space, where m and n are the line counts of the two files
- For large files (10,000+ lines), this is 10^8 operations — it will be slow
- Real Git uses the **xdiff** algorithm (Myers diff), which runs in O(n*d) where d = number of differences. For similar files, d is small, making it much faster.
- Did you hit this wall? What's the largest file you tested?

## Q5 — Command Pattern Justification

> "You used the Command Pattern for each Git command (add, commit, log, etc.). What would break — or what would become harder — if you'd just used a switch statement or if-else chain instead?"

*Expected:*
- Switch statement: adding a new command requires modifying the main dispatch block (violates Open/Closed Principle)
- Command Pattern: each command is a class with an `execute()` method — adding a new command = adding a new class, no modifications to existing code
- Future extension: with the Command Pattern, adding `unexecute()` to each command gives you undo for free — impossible with a switch
- Testing: each command can be unit-tested in isolation — a switch block tests everything together
